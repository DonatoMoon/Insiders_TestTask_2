# To-Do App (Разом) — Design Spec

Дата: 2026-08-12
Джерело вимог: `ТЗ.txt` (корінь `D:\Web\test\Insiders2`)
Процес: superpowers:brainstorming (без GSD)
Дизайн-прев'ю: HTML+CSS мокап опубліковано як Artifact (окремо від коду, для затвердження напряму перед розробкою)

## 1. Мета проєкту

Веб-додаток для управління завданнями (To-Do App) з підтримкою спільних списків і ролей учасників (Owner / Admin / Viewer). Тестове завдання, оцінюється якість коду, архітектура, іменування, грамотне використання бібліотек, логіка та UI-деталі.

Часових обмежень немає. Деліверабл: репозиторій + деплой на Vercel.

## 2. Функціональні вимоги (з ТЗ)

1. **Реєстрація/авторизація**: форма реєстрації (name, email, password), форма входу, персистентна сесія через токени.
2. **Списки завдань**: створення (назва), редагування назви, видалення.
3. **Завдання**: додавання (назва + опис), редагування, видалення, toggle виконано/не виконано.
4. **Ролі співучасників** (додаються за email до конкретного списку):
   - **Admin**: створює/редагує/видаляє завдання, toggle статусу.
   - **Viewer**: лише перегляд + toggle статусу.

## 3. Рішення, ухвалені під час брейнштормінгу

### 3.1 Ролі — три рівні, не два
ТЗ згадує лише Admin/Viewer для співучасників, але не визначає статус творця списку. Ухвалено:

| Роль | Хто отримує | Права |
|---|---|---|
| **Owner** | Автоматично — той, хто створив список | Редагувати назву/видалити список, додавати/прибирати учасників, повний CRUD завдань, toggle |
| **Admin** | Додається Owner'ом за email | CRUD завдань (назва/опис), toggle статусу |
| **Viewer** | Додається Owner'ом за email | Лише перегляд + toggle статусу |

Обґрунтування: розділяє "керування списком як сутністю" (Owner) від "керування вмістом списку" (Admin) — чистіша модель прав, ніж один "Admin" що робить і те, і те.

- Лише **Owner** може додавати нових співучасників (не Admin) — простіша модель прав.
- Owner може прибрати учасника зі списку (логічне продовження права "додає" з ТЗ; не було явно вимогою — позначено як припущення, узгоджене з користувачем).
- Якщо Owner вводить email людини без акаунту — показуємо помилку "користувача не знайдено" (без pending-запрошень; спрощення для обсягу задачі).

### 3.2 Токени авторизації
Firebase Auth SDK сам персистить сесію (`browserLocalPersistence`, IndexedDB) і сам рефрешить ID-токен. Ручного `localStorage`-менеджменту токенів немає — вимога ТЗ "збереження стану авторизації за допомогою токенів" закривається нативним механізмом Firebase, без саморобних рішень.

### 3.3 Модель даних Firestore

```
users/{uid}                    — { email, name, createdAt }
lists/{listId}                 — { title, ownerId, members: { [uid]: 'owner'|'admin'|'viewer' }, createdAt }
lists/{listId}/tasks/{taskId}  — { title, description, completed, createdAt, updatedAt }
```

- `users` — публічний індекс (uid ↔ email) для lookup при додаванні співучасника за email. Без цього клієнт не може знайти чужий `uid` за email (Admin SDK для такого lookup недоступний на клієнті).
- **Завдання — subcollection**, не масив у документі списку: точковий realtime-listener на кожну задачу, без переписування всього списку при редагуванні однієї задачі, без ризику впертись у ліміт розміру документа.
- **Members — map-поле** на документі списку (не окрема колекція `memberships`): "мої списки" читається запитом `where('members.' + myUid, '!=', null)` — Firestore підтримує dot-path запит по відомому на клієнті uid. Окрема колекція `memberships` розглядалась і відхилена як over-engineering для обсягу задачі (масштабується краще, але додає зайву колекцію/write'и/rules без реальної вигоди зараз).

### 3.4 Права доступу — Firestore Security Rules як source of truth
UI ховає/дизейблить елементи за роллю, але **реальний захист — security rules**, не клієнтський код:

- `lists`: read/write — лише member. Edit title / delete / member-management — лише `members[uid] == 'owner'`.
- `lists/{id}/tasks`: read — будь-який member батьківського списку (`get()` на `lists/{id}`). Create/update/delete — `owner` або `admin`. Для `viewer` дозволений лише **point-update** поля `completed` (rule перевіряє `request.resource.data.diff(resource.data).affectedKeys().hasOnly(['completed'])`).

### 3.5 Синхронізація даних
Realtime `onSnapshot`-лістенери (не React Query + ручний refetch) — живі оновлення без рефрешу, узгоджено з природою Firestore. Підписки scoped до сторінки/компонента через custom hooks, живуть, поки компонент змонтований.

### 3.6 State management
- **Zustand** — тільки для auth/UI state (поточний користувач, стан завантаження auth).
- Дані списків/завдань — НЕ в глобальному сторі; кожен custom hook (`useLists`, `useListDetail`) керує власною Firestore-підпискою, скоуплено до сторінки. Firestore SDK вже виконує роль client-side cache — окремий caching-шар (React Query) визнано зайвим при realtime-підході.

### 3.7 Форми
`react-hook-form` + `zod` — типобезпечна схема-валідація (email формат, мін. довжина пароля, required-поля), мінімум ре-рендерів.

### 3.8 Структура екранів
Dashboard (`/lists` — картки всіх доступних списків з позначкою ролі) → окрема сторінка списку (`/lists/[listId]` — задачі конкретного списку). Паттерн на кшталт Trello/Notion, а не single-page sidebar-layout (простіше в реалізації, чіткіший поділ відповідальності сторінок).

### 3.9 Тести
Без тестів — фокус на фічі та UI-полірування (свідоме рішення користувача; ТЗ тестів не вимагає).

### 3.10 Мова інтерфейсу
Весь UI застосунку — **англійською** (явна вимога користувача). Це також знімає обмеження з вибору шрифтів (кирилиця більше не обов'язкова), але дисплей/боді-пара Unbounded + Golos Text + Caveat залишається — вона вже обрана свідомо, працює і в латиниці, і продовжує уникати кліше "крем+serif+теракота".

### 3.11 Toast-нотифікації — нова залежність
**`sonner`** — бібліотека toast-повідомлень для React/Next.js. Обрана за мінімальний API (`toast.success()`, `toast.error()`), легку кастомізацію вигляду під наші токени, вбудований stacking/auto-dismiss. Використовується для фідбеку після create/update/delete-операцій (список, завдання, учасник).

### 3.12 Модальні патерни (UI-контракт)
Формалізовано у прев'ю v2, переноситься 1:1 в реалізацію:
- **Create/Rename list modal** — одне поле (назва), Cancel/Create.
- **Task modal** (create ТА edit — один компонент, різниться лише заголовком і префілом) — назва + опис (textarea), Cancel/Save.
- **Add member modal** — email + вибір ролі (Admin/Viewer; Owner не признач.), Cancel/Send invite.
- **Confirm-delete modal** — один переюзаний компонент для task/list/member, копія (заголовок/тіло/текст кнопки) підставляється за контекстом видалення. Warning-іконка, Cancel + Delete(danger).

Усі модалки — keyboard-доступні (Escape закриває, backdrop-click закриває), реалізуються як контрольований React-компонент (`open`/`onOpenChange` state), не через CSS `:target` — той трюк використано лише в статичному HTML-прев'ю для імітації сторінок без JS-фреймворка й не переноситься в код.

## 4. Архітектура проєкту (Next.js App Router)

```
src/app/(auth)/login/page.tsx
src/app/(auth)/register/page.tsx
src/app/(app)/layout.tsx              — auth-guard (onAuthStateChanged + redirect)
src/app/(app)/lists/page.tsx          — dashboard
src/app/(app)/lists/[listId]/page.tsx — задачі конкретного списку

src/components/auth/      — LoginForm, RegisterForm
src/components/lists/     — ListCard, CreateListDialog, ListTitleEditor, MembersPanel, AddMemberForm
src/components/tasks/     — TaskItem, TaskForm, TaskList
src/components/ui/        — дрібні примітиви (Button, Input, Modal, Badge…)

src/hooks/                — useAuth, useLists, useListDetail, useTasks
src/lib/firebase/         — ініціалізація клієнта
src/lib/firestore/        — CRUD-функції поверх SDK (lists.ts, tasks.ts, users.ts)
src/lib/validation/       — zod-схеми
src/lib/types/            — List, Task, Role, Member

src/store/authStore.ts    — Zustand
```

Auth-guard — клієнтський (onAuthStateChanged у layout), без SSR session-cookie (Firebase client auth живе в IndexedDB, недоступний у middleware/edge без додаткової cookie-синхронізації — визнано зайвим ускладненням для обсягу задачі).

## 5. Візуальний напрям — "Разом" (тепле, не шаблонне)

Продуктова назва мокапу: **Разом** (спільні списки справ). Дизайн-прев'ю опубліковано окремо як статичний HTML+CSS Artifact — до початку кодування застосунку.

### 5.1 Чому не "типовий" warm-дизайн
Комбінація "тепла near-white/крем основа + serif-заголовки + теракотовий акцент" — один з найпоширеніших AI-генерованих паттернів. Щоб уникнути цього, дисплей-шрифт свідомо зміщено від delicate-serif (Playfair/Fraunces) до геометричного display-шрифту з характером (Unbounded), а базовий фон — ближче до білого (не глибокий крем), як просив користувач.

**Технічне обмеження, що вплинуло на вибір шрифтів**: контент українською — Fraunces/Karla (початковий варіант) **не мають кирилиці**. Перевірено напряму через Google Fonts CSS API. Тому фінальний вибір:

### 5.2 Токени

```css
--bg:            #FAF8F4   /* теплий near-white */
--surface:       #FFFFFF
--ink:           #2A2118   /* теплий charcoal, не #000 */
--ink-soft:      #6B6153
--accent:        #C1502E   /* насичений paprika/burnt-orange — CTA, owner */
--accent-text:   #9C4020   /* темніший варіант для тексту (контраст) */
--gold:          #B8873A   /* admin */
--sage:          #6E7F5C   /* viewer + completed-state */
--line:          #E6DFD2
```
Жодного blue/purple/indigo — свідома відмова від типового SaaS-вигляду (явна вимога користувача).

### 5.3 Типографіка (з підтримкою кирилиці — перевірено)
- **Display** (заголовки, wordmark): `Unbounded` — геометричний display з характером (400–800), не заезжений Playfair/Fraunces.
- **Body** (UI-текст): `Golos Text` — гуманістичний grotesk, кирилиця нативна, без "Inter-клон" відчуття.
- **Handwritten-акцент** (теги, підписи, tagline): `Caveat` — лише для дрібних приміток, ніколи для основного контенту (a11y).

Усі три шрифти вбудовано в прев'ю як base64 `@font-face` data URI (cyrillic + latin subset), бо CDN-лінки на шрифти заблоковані CSP артефактів.

### 5.4 Диференціатор
Чекбокс задачі — SVG stroke-dashoffset анімація "намальованого чорнилом" чекмарку, а не заповнення квадрата. Виконана задача перекреслюється рукописною лінією (той самий прийом, transform: scaleX). Це головна "запам'ятовувана" деталь інтерфейсу.

### 5.5 Композиція
- Dashboard: картки списків з легким випадковим нахилом (`rotate(-1.5°…1.5°)`), на hover — вирівнюються + тепла тінь.
- Задачі — картки з "прошитим" лівим краєм (dashed border + punch-hole патерн), не голі рядки.
- Ролі — не текстові pill-бейджі, а "печатки"-стемпи: колір + іконка (ключ/гайковий ключ/око) — не лише колір, для a11y.
- Прогрес списку — ряд "тіків" (заповнені/порожні квадратики), не звичайний градієнтний progress-bar.
- Легка grain/noise текстура на фоні (SVG feTurbulence, opacity ~0.05) — глибина без затемнення.

### 5.6 Motion
Один продуманий staggered reveal карток при завантаженні (fade+rise+rotate-in, delay ~50-70ms/картка) замість розкиданих мікроанімацій по всьому UI. `prefers-reduced-motion` — анімації вимикаються.

### 5.7 Тема
Свідомо **single-theme** (світла, near-white) — не light/dark toggle. Ужитковий "паперовий" світ як цілісна концепція, а не перемикач; узгоджено з користувачем (обрав світлу основу, не toggle).

### 5.8 Ревізія прев'ю v2 (після фідбеку користувача)
- Ширший контейнер (1360px, було 860px), збільшена типографічна шкала і padding'и — на 100% zoom елементи читаються комфортно.
- Header (лого, nav, пошук, дзвіночок, avatar-dropdown) і footer (брендинг + колонки посилань) — повноцінний "site chrome", не мінімальний топбар.
- Dashboard і сторінка списку розділені на окремі "сторінки" (в прев'ю — через CSS `:target`-роутинг без JS; у реалізації — це вже й так були окремі Next.js routes `/lists` і `/lists/[listId]`, розбіжність була лише в статичному мокапі).
- Додано login/register сторінки зі split-panel макетом (бренд-панель + форма).
- Виправлено різну висоту карток у "хто що бачить" — `.compare__col` тепер flex-колонка, `.task` розтягується на всю висоту.

## 6. Поза межами обсягу (явно виключено)

- Pending-запрошення співучасників за email без акаунту.
- Передача Owner-статусу іншому учаснику.
- Unit/e2e тести.
- SSR session-cookie для auth-guard (лише client-side redirect).
- Dark theme / theme switcher.
- Markdown/rich text в описі завдання (простий текст).
